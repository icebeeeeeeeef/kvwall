# 接下来只做这一件事：前置知识 + 第一个 kvwall 闭环

日期：2026-09-25。性质：讨论后的执行备忘，**不是已经实现的功能或实验报告**。依据 [学习路线](../../plan/09-learning-roadmap.md) 与 [主线](../../plan/02-mainline.md)；规划修订见本仓库 PR #2，方向规则以合并后的 plan 为准。

## 1. 我的近期目标

**用一个小模型、一个多轮负载和现成 vLLM，搭出能够复跑、能确认前缀命中、能做性能评测的最小系统。**

我不是现在就写推理引擎、KV 存储服务或优化算法。前置知识与搭建交错完成：先运行一个请求，遇到具体问题再补；下面的小产出齐了，第一版也应基本搭成。

## 2. 前置知识：学什么，做到什么就先停

| 主要内容 | 这一部分完成时，我能做到什么 |
|---|---|
| **Transformer 推理与 KV**：token、prefill/decode、attention、KV 的内容与复用条件 | 画出一次 prefill 和后续 decode；复用 HF 小模型写带/不带 cache 的 decode 循环，在相同输入/dtype/backend 下比较每步 logits，说明误差容限；不用从零写 Transformer |
| **一个模型的容量**：权重、KV、运行时预留；dense/GQA 的层数、KV 头、head_dim、dtype | 从 config 手算 bytes/token，写一个容量估算脚本；解释为什么可驻留 token 数不是直接等于可服务并发 |
| **PyTorch/CUDA 最小集**：shape/stride、dtype/device、pinned memory、异步提交与完成 | 写一个带预热和正确同步边界的 H2D/D2H 计时脚本；能说清测到的是提交成本还是传输完成，不必先学完多流优化 |
| **vLLM 最短请求路径**：调度、block 分配、prefix 命中、执行、完成/释放 | 沿实际类/函数解释一条冷请求和一条热请求，用日志/指标证明命中；不先通读所有 connector、worker 和 kernel |
| **评测基本口径**：会话/请求、并发/gap、TTFT、TPOT、ITL、失败、预热与重复 | 给固定负载做一次小扫描，保留所有请求终态和原始数据；知道流式 chunk 不一定等于一个 token，少量样本不能证明稳定 p99 |
| **硬件路径概览**：显存、DRAM、SSD、网络，以及 PCIe/NVLink/RDMA/GDS/CXL 的作用边界 | 画清数据从哪到哪、经过哪些 buffer；能判断某技术可能影响哪段成本、明显不解决什么。现在不要求配置 RDMA/GDS 或学习所有协议 |

阅读只为完成这些小产出服务。MLA/混合模型细节、KV 量化落地、推测解码、FlashAttention 实现、PD、io_uring/SPDK 深入都不是第一版开工门槛；后续有需求或现象再展开。

## 3. 最小项目长什么样

```text
可复现的多轮 agent-like 请求（我定义/适配）
                    ↓
stock vLLM + 一个固定小模型
GPU-resident KV + prefix caching，无外部 KV 卸载
                    ↓
逐请求结果 + 原始 metrics + manifest（我保存）
                    ↓
容量估算 + 延迟/goodput/命中曲线（我分析）
```

**复用的**：模型、推理引擎、attention 实现、原生 GPU allocator 与 prefix cache、适合的现成压测工具。

**自己维护的最少代码**：多轮负载定义/薄适配、扫描 runner、指标与运行清单、容量脚本、SLO 统计/画图。先用简单脚本，不先开发通用平台或完整 agent。

**暂时不做**：CPU/SSD/远端 KV 后端、PD、router、Grafana、自研通信库、完整 kernel 或必须提一条 PR。它们不是这份笔记的验收条件。

## 4. 第一轮怎么搭、怎么测

**环境和模型。** 本地 RTX 4060 先选能装下的 0.5B～1.5B dense/GQA 模型，固定 revision/tokenizer 和 vLLM 版本；具体能否运行以实测为准，不坚持 7B。WSL 可做适用的开发/机制验证；需要原生内核或设备能力时再换 Linux/租卡。记录实际 backend、dtype、chunked prefill 和 CUDA graph，不把默认配置当未知。

**负载。** 固定会话轮数、首轮长度、每轮新增输入、输出长度、轮间 gap、共享前缀和随机种子，明确标为 synthetic agent-like。起步不依赖获得真实 trace。性能对照用相同 token 回放；用前轮真实输出构造下一轮时另做语义验证，避免输出变化悄悄改变 A/B 工作量。共享前缀按 tokenizer 的真实 token 序列检查，不能只看字符串相似。

**先验路径。** 做冷请求、相同前缀热请求、清空/绕过缓存对照。热请求必须出现实际 prefix hit；冷和绕过组应符合无命中的设置。输出正常不是命中证据，TTFT 变快也不是唯一证据。

**再扫并发。** 例如从 1、2、4 起步，在显存/时长/失败率安全范围内增加点；这是起步示例，不是固定容量结论。每点从三次重复起步，控制预热和缓存状态，首轮/后续轮分开，保留成功、失败、超时与结束时仍在途的请求。

**先定判据。** 测前写明 TTFT/TPOT 的 X/Y 阈值和容许失败率。报告成功延迟、失败率、goodput、命中与 KV/队列/抢占证据。逐 token 时间拿不到就明确只测到 chunk 间隔；样本不足时把 p99 标为探索性。

**最后解释。** 对比容量估算与实测。若变慢来自计算或排队，不叫 HBM wall；若没有测到失效点，报告当前下界。必要时安全缩小测试 KV 预算或扩大工作集，并记录人为限制，不为了出现墙直接购买更多硬件。
