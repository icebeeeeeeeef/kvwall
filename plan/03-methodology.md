# 03 方法论：正确性、路径证据与性能闭环

2026-09-25 修订，依据 D-020 / D-022 / D-024。第一版可以没有性能优化；先建立可信基线，再形成后续干预的闭环。

## 1. 闭环的八步骨架

1. **先定义问题或需求**：负载、资源、SLO 与待验证行为；新模型/配置适配不必先证明性能瓶颈。
2. **先算数量级**：权重、KV、运行时预留与工作集分开；按实际布局和 rank 核算，估算注明假设。
3. **选真实替代方案**：主要 A/B 使用同配置的合理 stock 系统；单独的机制对照可以关闭功能，但必须说明。
4. **先验正确性和实际路径**：配置开启、API 成功、模型能回答、真实缓存命中是不同证据。
5. **隔离变量并扫范围**：找拐点，不只比较一个恰好有利的点；记录未跨越边界的情形。
6. **分解机制与副作用**：排队、提交、数据搬运、同步、重算，以及其他请求的 ITL、CPU/RAM 和质量。
7. **按证据改一处并复验**：也允许证明原假设错误或当前方案没有收益；不为正向数字扩大设计。
8. **保留可复現性和边界**：每个结果可回溯 run_id、代码/模型/工具版本、硬件和原始数据。

## 2. 两种完成标准

**第一版 baseline 完成**：服务可重跑；冷/热/绕过行为可区分；固定多轮负载有重复扫描、原始结果、容量估算和已测 SLO 边界；对无法归因的现象诚实列出下一次实验。它不要求先修改引擎或证明提速。

**后续优化/适配闭环完成**：有合理 baseline；原因有路径/profiler/测试证据；至少一个干预（可为负结果）及回归；有正确性、失败处理、副作用和适用范围。若只完成兼容验证，就明确不宣称实现了新功能。

## 3. 指标定义：先约定再测量

| 指标 | 口径 |
|---|---|
| SLO 下的已测最大会话并发 | 在固定多轮/gap/输出/缓存状态下，已测试并满足 p99 TTFT≤X、p99 TPOT≤Y 及预定失败率约束的最大并发点；不是精确全局最大值 |
| TTFT | 从客户端发出请求到收到第一个有效生成输出的时间；说明网络/排队是否包括在内 |
| 每请求 TPOT | 多于一个输出 token 时，(最后输出时间−第一输出时间)/(输出 token 数−1)；单 token 请求记不适用，不伪填零 |
| ITL | 相邻输出 token 的间隔；客户端流式事件可能合并多个 token，此时只能报告 chunk 间隔或取得引擎 token 时间，不能冒充逐 token ITL |
| goodput | 单位时间内成功且满足约定逐请求阈值的请求数；与基于总体 p99 的容量判定分开。单 token/缺少时间戳的处理预先定义 |
| 失败/超时/取消 | 保留所有提交请求的终态和原因；不从分母静默删除；timeout 不能当作一个完整的真实延迟样本 |
| 前缀/分层命中 | 区分 query/hit、logical token 与各 rank 副本计数；实际恢复量与重算量一起看 |
| 传输/IO | 有效字节、队列等待、提交、实际操作与完成通知分别记录；并发重叠时不简单相加或用平均带宽相减归因 |
| GPU/host 占用 | 活跃引用、可驱逐缓存、in-flight staging 和非 KV 占用尽可能分开 |
| 逻辑 token 吞吐 | 标明是否含 prefix-cached prompt token，不能当实际模型计算量 |
| 交叉区间 | 实测回载与重算曲线的交叉；可以不存在/不唯一，未跨越只报告当前范围 |

会话数、请求并发与到达率不是同一指标。多轮 closed-loop 需固定轮间 gap；open-loop 必须记录计划/实际发送时间与客户端积压，不让客户端跟不上掩盖排队。首轮与后续轮分别统计；需要合并时说明权重。

X/Y 是在测量前声明的实验或产品假设，可做两组敏感性对照。trace 描述负载，不自动给出可接受延迟。具体 metric 名称及分母以固定引擎版本为准。

## 4. 正确性与真实路径验收

首版至少做冷、相同前缀热请求、清空/绕过缓存三种对照：热请求需要非零命中证据；另外两种有对应控制。后续每接一层，强制让上层不再持有目标副本，再确认 CPU/SSD/远端实际恢复，而不是 GPU 命中或静默重算。

对字节搬运、布局转换优先逐字节/张量检查；对模型输出按相同 dtype/backend 的参考路径检查 token/logits 并声明容差与非确定性。dummy weights 可验证控制流/接口，不能证明真实模型质量。量化路径先与同量化 stock 对照，再单独评估量化相对高精度的质量变化。

生命周期测试从首次异步卸载就加入：

- 请求取消/超时后，设备仍可能访问 buffer；必须等安全完成或确认取消后才释放。
- 驱逐、读取、重复加载、晚到完成并发时，引用与 generation/任务身份不能混淆。
- 短读、部分失败、队列/空间满、reset/shutdown 不发布半成品、不无限扩张、不静默丢终态。
- 失败回退重算的代价也计入服务表现，不把故障只转换成「缓存 miss」后忽略。

只测试已经接入的路径，不在第一步实现所有分布式故障。新测试尽量有失败前/通过后对照或敏感性检查；受硬件条件限制时说明 CI 不能证明什么。

## 5. 测量卫生

- 固定模型 revision、引擎/原生扩展、依赖与实际 backend；两臂除目标改动外保持一致。
- 预热和缓存状态分开设计。重启/清理或使用受控数据，避免前一个扫描点污染后一个点；冷态和稳态都可研究，不能混算。
- 每个点从至少三次重复起步，可用交替 A/B 顺序；记录有效请求数、输出 token 数、原始分布和每次结果。固定 5–10 分钟或三次重复不保证 p99 稳定，样本少就标探索性。
- 不平均多个 p99 冒充总体 p99；多轮样本相关性也要说明，必要时延长运行或做会话级重采样。
- 成功延迟与所有请求终态一起报告，停止实验时处理并报告仍在途的请求，不只挑已完成快请求。
- 原始 metrics 抓取频率按机制选择；短暂争用需要时间线/事件，15–30 秒平均采样不能证明没有尖峰。
- GPU 时钟/温度/功耗、PCIe 链路、NUMA、磁盘/网络共享、容器/主机内存限制和 profiler 开销都记录。
- 故障注入用于正确性/可用性，正常路径性能另跑；不能将人为延迟计为真实生产收益。

## 6. 差距分析

```text
同机通用微基准：在该环境的可达水平
→ 保持引擎 chunk/layout/并发的访问模式微基准
→ 引擎真实路径：等待、操作、同步、回收
→ 能区分解释的干预
→ 回归、端到端效果与失效范围
```

先问时间是否真的在目标路径，再问资源是否限制了关键路径。低平均利用率不排除短时争用/延迟限制，高利用率不自动证明其决定端到端性能。新硬件实验需要明确它改变什么、如何确认路径、什么结果会停止扩大投入；不要求预先保证提速。

## 7. 文章模板与反模式

writeup 固定记录：问题与假设、设置与算术、baseline、正确性与路径、扫描结果、机制与副作用、边界、复现附录。文字平实，每个数字有定义。

避免：把合成负载称真实 trace；只报饱和吞吐；将开启配置当命中；将局部微基准当端到端收益；将 cache hit 当免除所有恢复成本；无证据声称 HBM/PCIe bound；以大模型/多机规模代替方法论；把上游作者数据写成本人成果。

概念笔记进 notes 用于学习，不替代上述证据，也不是禁止学习性解释。

## 8. 运行清单与数据

使用 `data/manifest.template.yaml` 起步；实现时在兼容基础上扩充所需字段，不把本文件中的示意字段当已实现 CLI/schema。

```text
run_id、日期、实验类型与结论范围
hardware：GPU/CPU/RAM、PCIe/NUMA、盘型/路径、NIC、虚拟化/权限
software：commit、原生扩展、驱动/CUDA、OS/kernel、backend 与实际启用功能
model：名称/revision、权重 dtype、KV dtype、TP/DP/EP 和布局
workload：来源/revision/许可、synthetic 标签、seed、轮数/长度/gap/共享规则
sweep：变量/点、冷热状态、预热、有效窗口、重复、SLO/失败率阈值
完整启动命令、客户端版本、指标分母与采样方式
原始请求/metrics/trace 路径与校验和、失败/超时/在途处理、异常记录
```

统一落到 `data/runs/<run_id>/`；大文件可外存但能定位，公开仓库不含凭证或敏感 prompt。小模型/单卡数据可正式记录，结论只对相应环境成立。
