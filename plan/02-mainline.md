# 02 技术主线

**《KV 容量墙：从 GPU 显存到远端池，SLO 约束下的并发前沿与每一层的数据路径》**

2026-09-25：依 D-020～D-024 保留章节问题和主线，调整开工门槛、规模解释与验证边界。下文的多卡/多机配置是扩展验证候选，不是首个实验的必需配置；具体实现和硬件不预先锁定。

## 1. 脊柱问题

给定明确负载与 SLO，一套显存受限的推理服务能承载多少长上下文多轮会话？增加或改变 KV 存储、复用与传输机制后，这个边界移动多少、付出什么代价、在哪里失效？

每章回答一组相关问题，不预设每加一层必然提速或扩大容量。先研究现象，再决定是否修改软件或引入硬件。

## 2. 设计原则

1. **最小可验证配置**：小模型/单卡可验证真实机制；TP 分片、硬件 RDMA、独立实例性能需要对应资源，不能跨范围外推。
2. **平台与工程责任分开**：长期维护回放、统计、微基准与容量模型；最终逐步负责一处真实 KV 修改/适配及回归，不从零写整个引擎。
3. **先测可达水平，再解释引擎路径**：通用微基准、实际访问模式、端到端三种结果分开；差距不只可能来自带宽，也可能来自排队、同步和未使用目标路径。
4. **正确性先于收益**：冷/热/恢复/重算路径有证据；不完整对象不命中，在途资源不提前复用。
5. **保留合理 stock 对照**：主要结果在同模型、dtype、backend、资源和负载下比较；机制实验关闭功能时明确用途，不靠关闭原生优化制造优势。

## 3. 模型与硬件：候选而非启动条件

- **最小开发模型**：优先本地 RTX 4060 可运行的 0.5B～1.5B dense/GQA；确认实际 config、revision、context 限制和引擎兼容性。7B 不是固定要求。
- **扩展验证模型**：保留参考工作所用 30B-A3B 级 FP8 MoE 同族作为候选；具体名称与配置见 `08`，不能把同族估算当实际参数。
- **单节点扩展**：单卡起步，需要分片汇聚时 TP2，需要拓扑争用或两个 TP2 实例时 4×L20。卡型和拓扑写进 manifest。
- **多机扩展**：两节点及实际可用的目标网络，CPU-only 远端池可选；原两节点×4×L20 是较大验证点，不是所有 PD/共享实验的门槛。
- **架构适配**：在普通路径稳定后选择一种会改变 KV 假设的 MLA/滑动窗口/混合状态或推测模式，不同时扩成多条算法主线。
- **大模型单点**：8×L20 或 4×H20、235B-A22B 级模型仅作有问题意识的候选，能否运行需核算，不强制执行。

本文沿用 HBM wall 作为「显存容量墙」的研究简称；具体卡可能使用 GDDR，不能把层级名当成硬件内存类型。

## 4. 容量算术与边界

普通 attention、未考虑并行复制与特殊状态时：

```text
bytes_per_token = 2 (K,V) × L_kv_layers × H_kv × d_head × bytes_per_elem
resident_tokens ≈ KV_available_bytes / bytes_per_token
resident_sessions_at_L ≈ resident_tokens / L
```

**仅为算术示例**：假设 48 个 KV 层、4 KV 头、head_dim=128，则 BF16 是 98,304 bytes/token（96 KiB），FP8 纯 payload 是 49,152 bytes/token（48 KiB）。不是对尚未选择模型的参数声明；还需核对 scale、padding、分组、块取整与其他状态。

TP 或异构布局按 rank 核算，不默认聚合后平均分片：

```text
resident_tokens ≲ min_r(KV_available_bytes[r] / physical_KV_bytes_per_token[r])
```

权重、激活、CUDA graph 和其他运行时预留按实测记录。区分「可保存 token」「可保留不活跃会话前缀」「满足 SLO 的活跃负载」；共享前缀与轮间 gap 改变占用，resident_sessions 不是服务并发的直接预测。

磁盘/远端回载模型从下式起步，再由实测补排队、提交、同步与重叠：

```text
reload_time ≈ bytes / measured_effective_bandwidth + fixed_latency
recompute_time = measured_prefill_time
```

交叉点可能不存在或不唯一；没有跨过两条曲线时只给已测范围，不宣称找到了唯一 L*。容量、质量和延迟目标也可能使最优选择不同。

## 5. 章节

### Part I：单实例到同节点共享

#### Ch0 负载、指标与最小服务基线

- **问题**：会话多少轮、上下文如何增长、轮间 gap 和共享结构是什么；指标如何定义与复现。
- **首版**：stock vLLM + 一个小模型 + GPU-resident prefix cache + 多轮 agent-like workload。无外部 offload、无 PD、无远端服务；这就是后续对照的起点，不是自写引擎。
- **自己维护**：负载定义/现有工具适配、扫描 runner、原始请求/metrics/manifest、容量模型、SLO 统计与图。
- **负载来源**：可先 synthetic，明确标签和 token 构造；AgentX、Mooncake trace、参考博客脚本在许可/格式确认后接入。不因外部数据尚未获取阻塞开工。
- **出口**：冷/热/绕过对照，多个并发点的可重复评测、首轮/后续轮分开统计、原始结果和第一版预测对照。

#### Ch1 GPU 显存层：容量、前缀与抢占

- **问题**：prefix caching 开启时，服务容量边界在哪里；与算术差多少，原因是什么。
- **配置**：单卡可起步；TP2/TP4 是后续分片与资源验证。
- **工具**：KV 使用/命中、运行/等待队列、抢占/重算计数、GPU 内存、必要的 nsys 时间线；指标以 pin 为准。
- **旋钮**：工作集、并发、KV dtype、块大小、batch token 和 request 准入，逐项隔离。
- **验证**：FP8 KV 在兼容环境比较容量、质量和吞吐，不预设一定更快；没有抢占/容量证据不能把纯计算或排队拥塞称为显存墙。
- **JD**：容量与布局、量化落地、前缀复用、有效吞吐。

#### Ch2 主机内存层：恢复、搬运与调度干扰

- **问题**：启用原生 CPU KV 层后，保留与恢复带来什么收益；何时排队/传输/同步抵消重算收益。
- **配置**：单卡 + 足够 RAM 验恢复；TP≥2 验分片，多卡与 NUMA 争用由真实拓扑决定。
- **工具**：pinned/pageable、chunk、流/并发、NUMA 的访问模式微基准；记录提交等待、实际复制和完成通知；用 nsys 验重叠而非凭 Async 名称判断。
- **候选改造**：批量提交、buffer 管理、恢复优先级、在途字节预算、淘汰/预取。先接管原接口，不预写全部策略。
- **正确性**：源/目标引用、请求取消、晚到完成、池满和 reset；GPU 完成与存储完成不是同一事件。
- **副作用**：decode ITL/TPOT、CPU、host 内存与抢占；缓存模拟器、gather/scatter kernel 仅在能回答具体问题时写。
- **JD**：卸载、生命周期、调度、GPU 系统编程与数据搬运。

#### Ch3 存储层：回载与重算、布局和 IO 执行

- **问题**：fs/其他存储层在何种负载有效；恢复曲线与重算何时交叉；瓶颈是带宽、IOPS、元数据、排队还是复制。
- **配置**：可先云块设备，按问题选普通/高 IOPS 盘；本地物理 NVMe 可用时单独重跑，不混写结论。
- **工具**：fio、O_DIRECT/io_uring、QD/bs、iostat、perf/py-spy；对齐、短 IO、每 IO CPU 成本和 page cache 明确。
- **候选工程**：现有后端改造或 out-of-tree 次级层；对象索引、布局、异步执行、任务/空间上限、完整发布、失败/关闭契约。新后端须有真实需求，不以写轮子为目标。
- **GDS 边界**：host-centric secondary tier 只能拿到 CPU 区域；SSD→GPU 需其他支持 GPU buffer 的 worker/connector 路径或已有实现。独立微基准/兼容模式与真实直通分别标注。
- **可选**：SPDK、对象存储、JuiceFS 路径在实际问题需要时比较，不强制全部接入。
- **JD**：NVMe/云盘、io_uring、布局、异构存储、全链路 IO。

#### Ch4 同节点多实例共享池

- **问题**：共享前缀是否真正跨实例恢复；共享收益与争用代价；多写者、驱逐与完整对象发布的语义。
- **配置**：CPU/小模型多进程可验功能；独立两 GPU 可做两实例性能；两实例均需 TP2 时才用四卡。
- **实现**：复用共享 fs 或 MooncakeStore；明确模型/revision/dtype/layout 身份、完成/失败、引用和跨进程资源所有权。
- **JD**：共享复用、KV 池、独立缓存服务集成。

### Part II：远端与 PD

#### Ch5 跨节点 KV 池、独立服务与可观测性

- **问题**：远端复用收益与查询/传输/排队代价；新实例从共享池恢复缓存的曲线，区别于加载权重的启动时间。
- **候选臂**：MooncakeStore standalone、vLLM p2p tier；只启用已验证兼容的组合。
- **先验路径**：元数据命中、远端副本可用、传输完成、目的端可读分别验证；先 CPU/协议测试，后实际 RNIC/perftest 与引擎传输。
- **工程**：注册内存与在途 buffer 生命周期、失败/取消、指标和告警；必要时改传输或服务子模块，不另建整套 master/Raft。
- **JD**：RDMA、分布式缓存、解耦服务、监控、跨节点共享。

#### Ch6 PD 分离

- **问题**：请求从 P 到 D 的交接如何改变 KV 放置、传输和调度；多轮下如何复用 D 端生成状态。
- **配置**：小模型同节点 1P+1D 可验交接，跨节点再验证目标网络；P/D 配比和大并发需要更多独立资源时才扩容。
- **候选对照**：GPU 直传与 host 中转；须确认实际路径、模型/布局兼容和可用后端，不因一种方式不可用就声称另一种是全系统唯一方案。
- **责任**：目的端预留、描述符/分片、部分完成、失败后重算对其他 D 请求的干扰、取消和源端释放。
- **JD**：PD 池化、KV 高速传输、生命周期与一致性。

#### Ch7 cache-aware 路由

- **问题**：命中、恢复成本与实例活跃负载如何取舍；缓存事件过期或丢失时会怎样。
- **实现**：复用 Dynamo/SGLang 等 router，必要时定点修改；至少两实例才能比较路由，更多实例的边界另测。不自建完整 agent 平台，不默认引入 k8s。
- **JD**：全局管理、准入/背压、事件与缓存感知调度。

### Part III：代表性配置与架构适配

#### Ch8 换一种会改变 KV 假设的配置重验

- 在 MLA、滑动窗口/混合状态、推测模式中按需求选择一个代表性适配；检查 layout、分配、有效范围、前缀身份、恢复与回滚，而非只换模型名。
- 量化验证区分同量化配置下存取正确性与量化本身质量变化；权重量化不等于 KV 量化。
- 这类小范围兼容验证可因真实需求提前，不必等全部多机章节完成；不把每种架构都加入首版前置。

#### Ch9 可选：大模型一个验证点

- 仅在它能回答小配置未回答的问题时执行，不做大模型全矩阵扫描。

## 6. 规模与证据

| 要证明的事情 | 最小路径 | 不应外推 |
|---|---|---|
| 前缀命中、淘汰、CPU/磁盘恢复 | 小模型单卡；状态机可 CPU 测 | 多卡/数据中心吞吐 |
| TP 分片与布局 | 实际 TP≥2 的兼容模型 | 任意 TP/backend 通用性 |
| 多卡 PCIe/NUMA 争用 | 真实共享拓扑上的多卡并发 | 「四卡一定存在同一种瓶颈」 |
| 多实例共享与多写者语义 | 同节点多进程 + 存储进程 | 独立 GPU 性能隔离 |
| PD 交接 | 两逻辑实例；性能用独立资源 | 跨节点 RDMA/生产容量 |
| RDMA/GDS 直接数据路径 | 实际支持的设备、驱动与后端 | Soft-RoCE/TCP/兼容模式等价 |

## 7. 阶段映射与成果出口

首版 Ch0 + Ch1 构成所有后续对照的最小平台。Part I 优先，Part II/III 是扩展，不改变「先单实例，再共享/多机」的主线。

有可信 baseline、真实路径、解释得清的干预/负结果、正确性回归，以及一处本人负责的修改/适配时即可整理投递材料，不等每章完成。实验报告与实现责任分开标明，不能把所有上游能力写成本人产出。

## 8. 与参考工作的关系

参考博客/PR 的模型、硬件、负载、功能支持可能变化，见 `06`。先复核原工作实际测了什么，再把以下作为研究候选，而不是未经核查的「别人没做过」声明：

- 显存受限的 PCIe 配置与不同 KV 预算；
- 云盘/本地 NVMe、不同访问粒度；
- 聚合服务中恢复对正在 decode 请求的干扰；
- 多轮负载下 SLO 边界、跨实例复用与缓存热启动；
- 分片汇聚、主机争用与 GPU 直传/host 中转的代价。

## 9. 风险与停止条件

每个对照钉 commit 与依赖；接口在代码上审计，不依赖 latest 文章。负结果与有效边界也算闭环；没有出现预想的墙时报告事实。性能不明先诊断，不先租更大硬件。扩展模型/后端/编排必须有问题或需求，避免回到全面预学与全面造系统。
