# 01 策略：方向、证据、阶段、对齐

2026-09-25：保留 KV / 内存层级与数据搬运的方向；学习、规模和成果出口按 D-020～D-024 更新。下述职业判断是本项目的策略假设，不是招聘方承诺或行业统计。

## 1. 背景与约束

- 985 本科；有字节火山引擎对象存储实习，后端/存储基础；深度学习、推理引擎与高速 IO 需要通过项目积累。
- 目标：国内推理团队的 KV cache / 分层存储 / IO / PD 池化方向，以此进入 AI infra；长期靠真实 ownership、生产经验与生态贡献接近核心团队。
- 资源：本地 RTX 4060，以及按需要租用单卡/多卡/多机的预算。资源多不意味着先扩大配置。
- 约束：不同时学习全部 AI Infra，也不把实现新模型、训练 draft 或完整 attention kernel 作为当前项目的必需目标。

## 2. 方向定义

不把自己局限为「会配置 KV offload」，而是研究 **LLM 推理的内存层级与数据搬运，以及它和调度、复用、模型状态的边界**。

主问题仍是长上下文多轮负载下的 KV 容量、恢复成本和 SLO。往上理解 scheduler/准入/路由，往下理解实际 buffer、布局、IO 和 kernel 接口；不要求从第一天就负责整个引擎。

模型和执行方式改变时，缓存假设可能失效。需求决定支持什么，正确性决定怎么支持，测量决定优化哪里；不把所有适配工作都伪装成性能瓶颈驱动。

## 3. 迁移逻辑：存储 → KV cache

| 存储基础 | KV 路径中的对应责任 |
|---|---|
| 多级存储、IO 与资源预算 | GPU 显存 / DRAM / SSD / 远端，回载与重算、在途字节 |
| 元数据与缓存身份 | prefix hash、模型/版本/layout 隔离、可读对象发布 |
| 并发与生命周期 | 引用、异步完成、取消、驱逐、重置、迟到事件 |
| 调优与可用性 | 队列、批量、尾延迟、限流/背压、失败回退 |
| 生产经验 | 将现象缩小、守住正确性、解释权衡，诚实区分实习与个人实验范围 |

这些是可迁移的方法，不意味着不同模型状态和并行拓扑的语义完全一样。最终需要一次实际适配/验证来检查迁移能力。

## 4. 证据哲学

### 4.1 同一条线

实验平台产生可复现的行为与数据；真实缺口形成上游修改/组件；报告解释结果与边界。PR、文章和个人项目不并行包装成三套无关经历。

首版的主体是验证设施，最终的工程主体是**一段本人能负责的真实 KV 执行路径**。这可以落在引擎、connector、worker、存储后端或传输模块，不强制新造整个系统。

### 4.2 检查维度，而非面试官评分公式

- 测量是否可信：原始数据、采样单位、失败口径、尾延迟、对照与重复。
- 解释是否有证据：路径、profiler、状态机、反例与干预，不只相关性。
- 需求是否具体：负载/约束/适配目标明确，不为技术标签设计。
- 本人责任是否可验证：修改了哪里，保障什么，哪些复用上游。
- 正确性与边界是否完整：不误用 KV、不泄漏、不无限等待，负结果诚实。
- 是否可复跑与审查：版本、测试、运行清单、设计讨论与已知限制。

不以代码量、模型大小、卡数、功能数、star 数或 PR 数量代替上述检查。

### 4.3 学习、验证、实现与生产经验分开

读教材、概念笔记、跑示例都有学习价值，但不自动构成实现经验；上游的测量不是本人的成果；单次演示不是生产成熟。

源码阅读可以产出路径图、最小复现、测试和具体改造，不要求先通读源码才开工。没有 PR 合并时，也可以如实展示代码、验证与讨论；不保证合并率或岗位结果。

### 4.4 小配置不等于玩具

| 不足的证据 | 有效的改进方式 |
|---|---|
| 只说服务能回答问题 | 验证冷/热/恢复路径，比较数据/输出和指标 |
| 合成负载不说明 | 固定 token/轮数/gap/共享规则，标 synthetic；有条件再接真实 trace |
| 单点或只报饱和吞吐 | 给出重复扫描、SLO、失败与副作用 |
| 本地结果外推集群 | 限定本地结论，再为 TP/RDMA 等特有问题升级资源 |
| 代码改完没有失败前对照 | 构造敏感性/回归测试，说明哪些硬件条件没覆盖 |

## 5. 阶段规划：按出口推进，不先等整套知识学完

| 阶段 | 目标 | 出口与后续 |
|---|---|---|
| 0 最小基线 | 前置知识与小服务交错完成 | stock vLLM GPU-resident KV、固定多轮负载、冷/热对照、容量脚本和重复评测。无外部后端/PD 要求 |
| 1 一条路径的工程证据 | 优先 Part I，逐步研究 CPU/存储/共享 | baseline、机制证据、真实修改或适配、正确性/失败回归、带 run_id 的结果；不等 Ch4 全完再整理投递 |
| 2 扩展与生产经验 | 按目标需求进入 PD/远端、代表性架构与开源协作 | 在更真实配置下接管模块与边界，不把更多机器本身当产出 |

时间安排由实际进度与求职窗口调整。原三周纯学习、三四个月后才投、所有章节全部完成等都不作硬门槛。达到当前可证明的能力即可投递与寻找反馈，同时继续深入。

## 6. 生态对齐

- 主引擎保留 vLLM，先读与当前请求相关的 KV 路径。
- 远端池优先复用 MooncakeStore / Transfer Engine，不同时新建自己的 master 和通信库。
- SGLang HiCache 可作为后续对照或具体适配的目标；LMCache、FlexKV、3FS 先读方案与相关 PR，不为广度同时部署全部。
- router/编排复用现成组件，不默认上 k8s。
- 面试反问 KV 组与 scheduler、存储、kernel 团队的边界；不要假定岗位需要一人负责整个栈。
- 核心团队长期目标保留；开源贡献与生产经验都是证据，不把任何一种经历称为唯一入口。

## 7. 执行规则

1. 性能优化记录实测问题；适配记录明确需求；正确性与资源边界不等性能批准。
2. 一次只负责一段可审查的改动，不为凑 JD 加所有后端/算法。
3. 负结果 + 解释与边界也算完成；但最终不能只有脚本而没有真实实现责任。
4. 本地/云、单卡/多卡、模拟/真实设备分别声明，未实测就明说。
5. 概念浏览用于建立认识，深入学习用于推进下一次实验；不在低相关知识上无限展开。
6. 研究上游需求时先看负责人、关联 PR 和最新讨论；不重复实现已有工作，不把认领数量当成果。
7. 上游修改可以保存在对应 fork，kvwall 保留运行、复现与证据，不为集中代码而复制整个项目。

## 8. 长期路径

主线：KV 层级与搬运 → 引擎内存管理/调度 → PD/集群管理。RL 数据搬运、weight sync、训练存储是后续可迁移方向，不当前并行开工。

kernel 保持能读接口、能 profile、必要时能改 KV 搬运/布局转换；完整 attention kernel 不作为当前主目标。切换方向需要真实需求和产出，而不是只新增学习清单。
