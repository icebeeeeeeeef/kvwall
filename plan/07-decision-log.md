# 07 决策日志

格式：编号 / 日期 / 状态（有效 · 已复审 · 已废止）/ 决定 / 背景 / 理由 / 代价 / 复审条件。

方向性决定先写这里，再改其他文件。「因为测到了 X」是优化功能类决定的必填项；适配需求与正确性工作记录需求/契约来源，不伪造性能观测。

## D-001 · 2026-09-18 · 有效 · 方向：推理侧 KV cache，边界定义为「内存层级与数据搬运」

- 背景：候选方向有预训练、后训练 / RL、推理；个人背景是后端 + 对象存储实习，无 DL / RL / 科研。
- 理由：KV cache 分层是穿着 LLM 外衣的存储系统问题，迁移成本最低；国内推理团队确有专门的 KV cache 组；边界划宽（含权重加载、PD 传输、weight sync）以对抗分层存储的商品化和模型架构变化。
- 代价：放弃直接冲 RL 系统；预训练算法侧不考虑。
- 复审条件：一年后根据实习实际接触到的问题复审是否往 RL 系统搭桥。

## D-002 · 2026-09-18 · 已复审 · 实验平台 + 从真实缺口中形成的组件，不做独立 KV 引擎

- 原背景：曾考虑做一个针对特定场景特化的 KV cache 引擎（对标 Mooncake / FlexKV，特化与简约）。
- 原理由：在测量之前确定特化形态，容易设计跑在数据前面；平台提供发现与可复现性，组件可通过现有系统交付。
- 2026-09-25 复审：平台是验证设施，不是最终工程能力的全部。D-024 要求逐步负责一段真实路径；先接管已有实现与契约，再由需求/证据决定修改，不提前另造大系统。
- 代价：需要写并维护真实集成、测试和异常处理，不能只运行 benchmark。
- 复审条件：多个闭环反复指向现有系统未覆盖的同一个需求，且形状与现有系统根本不同。

## D-003 · 2026-09-18 · 有效 · 主引擎 vLLM；SGLang HiCache 为阶段 2 对照臂；MooncakeStore 为远端池

- 背景：vLLM 与 SGLang 都主流；Mooncake 是本项目相关生态。
- 理由：vLLM tiered offloading 提供 host 中心、fs / obj / p2p、out-of-tree tier、指标与事件等工作面；SGLang 作为后续对照保留广度。
- 代价：首阶段只深入一个主引擎。
- 复审条件：阶段 2 或具体上游需求要求调整。学习相关 PR 不等于提前搭第二套主线。

## D-004 · 2026-09-18 · 已复审 · 2–4×L20 是多卡验证候选，不是正式数据的最低门槛

- 原决定：单实例正式单位为一节点 2–4×L20 TP2 / TP4；1×L20 + 7B 仅作开发。
- 原背景：希望观察 TP 分片汇聚与多卡争用，避免只有一次小模型 demo。
- 2026-09-25 复审：按待验证机制选最小配置，单卡结果可正式记录但不能外推多卡；同节点多进程可以验证共享语义。TP 分片需多卡，多卡争用取决于实际拓扑，不由固定卡数自动保证。见 D-021。
- 代价：每个结论必须写清模型、硬件、路径与负载范围。
- 复审条件：发现机制无法在当前配置触发，或需要扩展验证。

## D-005 · 2026-09-18 · 有效 · 扩展验证模型优先对齐参考工作，具体版本待确认

- 原决定：正式模型对齐 vLLM 博客所用 30B-A3B 级 FP8 MoE 同族。
- 理由：保留与框架作者对照的候选；不得把未核实的同族配置当成实际模型。
- 代价：MoE 的 TP / EP / DP-attention 需固定并声明。
- 2026-09-25 补充：不阻塞本地小模型起步；实际名称、revision、KV 布局和可用 backend 见 `08`，不是启动前必学全部架构。
- 复审条件：候选模型无法稳定运行或不能回答当前问题。

## D-006 · 2026-09-18 · 已复审 · 主线先单实例、再共享与多机；不以章节全完作为投递门槛

- 原决定：阶段 1 = Part I（Ch0–Ch4），Part II / III 后置。
- 理由：共享池与 PD 需要单实例基线才能归因，避免多条主线并行。
- 2026-09-25 复审：保留研究顺序，但达到可信 baseline、路径证据和一处真实修改/适配及回归即可整理成果；不等待 Ch4 或 RDMA 全部完成。见 D-024。
- 代价：阶段 1 未实测的 RDMA / PD 必须明确标注。
- 复审条件：目标岗位/上游需求改变优先级。

## D-007 · 2026-09-18 · 有效 · 主指标为 SLO 约束下的服务容量

- 理由：研究符合延迟要求的有效完成能力，不只报饱和吞吐。

## D-008 · 2026-09-18 · 已复审 · 优化由测量驱动，适配与正确性由需求/契约驱动

- 决定：提前建立路径与技术边界的认识；先跑请求，再补到能设计下一次验证；实施时深入接口。需求驱动适配与性能驱动优化分开记录。

## D-022 · 2026-09-25 · 有效 · 先验正确性与路径，再报告 SLO 边界

- 决定：从首个闭环区分冷/热/绕过，延迟分请求和逐 token，保留失败/超时；接 offload 后加入取消、部分失败、迟到完成、容量满和重置测试。
- 来源：输出正常和配置开启都不足以证明目标 KV 路径发生；固定时长/三次重复不保证 p99 稳定。
- 边界：没有抢占/容量等证据不把拥塞叫 HBM wall；有限扫描只给已测最大值/上下界，不宣称精确生产容量。
- 复审条件：新模型/路径改变正确性与完成契约。

## D-023 · 2026-09-25 · 有效 · 现代配置做代表性兼容，不追全面技术堆叠

- 决定：保留一段核心 KV 路径，后续做一种兼容量化 KV 的落地验证及一次改变缓存假设的代表性适配/验证；推测模式在相关需求出现时覆盖。

## D-024 · 2026-09-25 · 有效 · 区分最小实验基线与最终工程责任

- 决定：首版是 stock vLLM GPU-resident KV + 多轮负载 + 可重复评测，无外部卸载；自己先维护 runner/统计/容量/数据。之后逐步负责一处真实 KV 修改/适配及异常/回归，不必新造独立系统。
- 来源：最小项目必须可尽快搭建，同时最终不能只有配置与 benchmark。
- 边界：上游修复、窄适配和实际后端改造都可形成实现责任；不预指定必须自研某个后端，不以 PR 数量/合并或所有章节完工作为投递门槛。
- 复审条件：只有数据没有解释/实现责任，或实现范围开始脱离 KV 核心问题。
