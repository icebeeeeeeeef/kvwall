# 07 决策日志

格式：编号 / 日期 / 状态（有效 · 已复审 · 已废止）/ 决定 / 背景 / 理由 / 代价 / 复审条件。

方向性决定先写这里，再改其他文件。「因为测到了 X」是新增功能类决定的必填项。

## D-001 · 2026-09-18 · 有效 · 方向：推理侧 KV cache，边界定义为「内存层级与数据搬运」

- 背景：候选方向有预训练、后训练 / RL、推理；个人背景是后端 + 对象存储实习，无 DL / RL / 科研。
- 理由：KV cache 分层是穿着 LLM 外衣的存储系统问题，迁移成本最低；国内推理团队确有专门的 KV cache 组；边界划宽（含权重加载、PD 传输、weight sync）以对抗分层存储的商品化和模型架构变化。
- 代价：放弃直接冲 RL 系统；预训练算法侧不考虑。
- 复审条件：一年后根据实习实际接触到的问题复审是否往 RL 系统搭桥。

## D-002 · 2026-09-18 · 有效 · 长期项目形态：实验平台 + 从数据里长出来的组件，不做独立 KV 引擎

- 背景：曾考虑做一个针对特定场景特化的 KV cache 引擎（对标 Mooncake / FlexKV，特化与简约）。
- 理由：引擎的价值靳用户和生产验证，个人做不到；「特化」在测量之前无法确定，属于设计跑在数据前面；面试官会问「为什么不直接贡献给 Mooncake」。平台的价值靳发现与可复现性，且新模型 / 新硬件重跑成本极低。
- 代价：没有一个「我的系统」可以展示；组件以插件 / 后端形式存在。
- 复审条件：若多个闭环反复指向现有系统没填的同一个坑，且形状与现有系统根本不同。

## D-003 · 2026-09-18 · 有效 · 主引擎 vLLM；SGLang HiCache 为阶段 2 对照臂；MooncakeStore 为远端池

- 背景：vLLM 与 SGLang 都主流；Moonshot 栈是 SGLang + Mooncake。
- 理由：vLLM 本月发布的 tiered offloading 框架（host 中心、fs / obj / p2p、out-of-tree tier 接口、per-tier metrics、KV events）是现成的工作面，且作者测的 regime 是本项目的补集；MooncakeStore 已集成进 vLLM，保住 Moonshot 对齐；SGLang 作为对照臂保住广度。
- 代价：阶段 1 只懂一个引擎的源码。
- 复审条件：阶段 2 开始时评估是否需要把主引擎换成 SGLang（取决于目标团队）。

## D-004 · 2026-09-18 · 有效 · 单实例正式单位为一节点 2–4×L20 TP2 / TP4；1×L20 + 7B 仅作开发环境

- 背景：最初设计钉死在 1×L20；担心被判「玩具」。
- 理由：30B-A3B 级 FP8 模型在 1×L20 上只剩约 10 GB 给 KV，悬崖在并发 3，无代表性；2 卡约 17 个 64K 会话，4 卡约 44 个，与 vLLM 博客「64–128 会话开始分层」同阶。TP≥2 才存在分片汇聚，4 卡才存在多卡主机争用。
- 代价：正式测量成本上升；必须严格分离开发与测量时间。
- 复审条件：预算实际消耗超出粗估两倍。

## D-005 · 2026-09-18 · 有效 · 正式模型对齐 vLLM 博客所用 30B-A3B 级 FP8 MoE 同族

- 理由：生产真在跑的形态；与框架作者的结果可直接对读；在 2–4×L20 上内存真紧。
- 代价：MoE 引入 EP / DP-attention 的并行选择，需要在 Ch1 固定一个并行配置并声明。
- 复审条件：该模型在 2×L20 FP8 下无法稳定运行。

## D-006 · 2026-09-18 · 有效 · 顺序 Part I → II → III；阶段 1 = Part I（Ch0–Ch4）

- 理由：PD 与共享池建在同一套分层框架上，没有单实例基线无法归因；Part I 做完整比 Part II 做一半值钱；Ch4 用同节点两实例把「共享池」带进阶段 1 而不需要多机。
- 代价：阶段 1 简历上没有跨节点 RDMA 的实测。
- 复审条件：实习申请截止时间提前。

## D-007 · 2026-09-18 · 有效 · 主指标为 SLO 约束下的最大并发，不报饱和点吞吐

- 理由：饱和点吞吐比较的是没人会运行的 regime；SLO 约束下的容量是 infra 团队实际做的容量规划。
- 代价：需要先定 SLO（见开放问题）。

## D-008 · 2026-09-18 · 有效 · 无测量不加功能

- 理由：防止「为命中 JD 而设计」；每个功能的决策日志必须有「因为测到了 X」。

## D-009 · 2026-09-18 · 有效 · 不上 k8s 除非被迫；路由用现成组件

## D-010 · 2026-09-18 · 有效 · 不追最大模型；235B-A22B 级只跑一个验证点

- 理由：钱买不到新信息；大模型上扫描稀释归因。

## D-011 · 2026-09-18 · 有效 · 不依赖 GDS 与本地 NVMe；Ch3 以云块设备 + O_DIRECT / io_uring 起步，标注「云盘」

- 理由：云资源调研显示本地 NVMe 与 GDS 均不确定；IO 路径的软件侧在云盘上即可研究；可购时用同一平台重跑。
- 代价：磁盘层可能表现差——记为发现。

## D-012 · 2026-09-18 · 有效 · 阶段 1 只做一个闭环系列，不并行开第二条线

- 理由：一根线 > 五个碎片；分散是最常见的失败原因。

## D-013 · 2026-09-18 · 有效 · 训练侧存储（checkpoint / 数据加载 / 并行文件系统）作为备选入口，不并行推进

- 理由：与主线共享「数据搬运」内核；若推理侧实习未拿到，这条路对背景同等适配。

## D-014 · 2026-09-18 · 有效 · 「启动延迟 / 权重加载」不单开线，以「新实例从共享池热启动」并入 Ch5

- 理由：权重加载是另一个问题，混进 KV 主线会稀释；热启动是 tiered offloading 框架文档明确提到的用例，正当接入。

## D-015 · 2026-09-18 · 有效 · 文章文风对齐 vLLM 博客：平、准、每个数字带定义；不写概念科普

- 理由：营销式文风与核心团队评价负相关；概念科普是负分。

## D-016 · 2026-09-23 · 有效 · `micro/` 允许并鼓励按引擎访问模式构造的自研微基准（C++ / CUDA / liburing / verbs）

- 背景：D-008 与 `tiers/` 空置规则使阶段 1 几乎不产生底层代码；JD 要求 io_uring / RDMA / CUDA 的实践经验。fio / perftest 打出的是通用天花板，不是引擎具体访问模式（chunk 尺寸、文件布局、消息大小）下的天花板。
- 理由：自研微基准是测量工具不是功能，不违反 D-008；差距分析可拆为「硬件天花板 → 该访问模式天花板 → 引擎实际」两段，方法论更强；若数据指向自定义 tier，代码可复用。
- 代价：多一层需要维护与校验的代码；自研基准须先与 fio / perftest / 通用 memcpy 基准交叉验证，偏差须解释。
- 复审条件：自研基准的维护时间超过其对差距分析的贡献。

## D-017 · 2026-09-23 · 有效 · 开发环境必须是真 Linux（云上开发机），不用 WSL

- 背景：本地为 Windows + WSL。io_uring、perf、Soft-RoCE（`rdma_rxe`）、nsys 部分功能在 WSL2 上受限或需自编内核。
- 理由：开发环境与测量环境的内核与工具行为需一致，避免在 WSL 上调通、在云上失效。
- 代价：开发机租用成本；本地只用于写文档。
- 复审条件：本地改为原生 Linux。

## D-018 · 2026-09-23 · 有效 · 阶段 0 拆出 3 周预备期；CUDA 目标收窄为 runtime + 能读 paged kernel 接口

- 背景：阶段 0 原定 2 个月内完成引擎源码级理解、C++ / CUDA、平台骨架与小 PR；本人无 DL 基础，负担过重。
- 理由：预备期只学读懂 KV 路径与做 Ch0 算术所必需的内容（见 `09` §4），其余按章 just-in-time；kernel 实现不在主线（`01` §8 C），能读接口即可支撑「往下碰 kernel 接口」。
- 代价：阶段 0 整体后移约 1 周；kernel 实现层面的深度推迟到 Ch8 且只读。
- 复审条件：预备期完成标准三周内未达成。

## D-019 · 2026-09-23 · 有效 · SPDK 从「不覆盖」改为「项目外 L2 + 无硬件小实操」

- 背景：`05` §4 原判断「没有本地 NVMe 没意义」；但 SPDK 的 malloc / aio bdev 不需要 NVMe 硬件即可跑通编程模型，且 JD 中出现频率高。
- 理由：一两天成本换取能讲清 SPDK 与 io_uring 的差别与代价；不进入主线测量。
- 代价：极小；不产出正式数字。
- 复审条件：可购到带本地 NVMe 的机型时，评估是否升级为 Ch3 对照臂。
