# 05 JD 映射：知识、实践与本人责任

## 1. 目标 JD（所有者收集的去重归纳，不代表所有公司当前完整要求）

核心是 KV cache 的卸载、复用、调度与高速 IO：

1. 多级缓存：GPU 显存 → DRAM → 本地 NVMe → 分布式存储，提升可用容量和有效吞吐。
2. 全链路 IO 分析与 RDMA / GDS / 零拷贝 / CXL 等路径设计。
3. 生命周期、换入换出、迁移、前缀/滑动窗口、跨请求/实例共享。
4. PD 场景下的 KV 池化、传输、全局管理与一致性。
5. KV 量化/压缩、布局、淘汰与预取；适配模型状态变化。
6. 独立分布式缓存服务，与推理引擎解耦集成，具备监控/告警。
7. 部分岗位另要求 kernel、算子融合、推测解码或并行策略开发，不把这些默认为本项目全部职责。

相关基础：C/C++/Go/Rust 至少一门、算法与数据结构、Linux/网络/并发、profiling；深入一个推理引擎，并理解 Mooncake、3FS、FlexKV、LMCache 等的定位。

## 2. 证据状态不能互相替代

| 状态 | 可以怎么说 | 不能怎么说 |
|---|---|---|
| 理解 | 读过相关代码/方案，能解释原理和取舍 | 已落地该组件 |
| 复现/验证 | 在固定配置验证了行为、路径和输出 | 自己实现了已有功能 |
| 修改/适配 | 负责具体接口/模块，有回归和边界证据 | 自己实现了整个引擎/缓存服务 |
| 真实设备测量 | 在指定硬件上测过数据路径 | 从 Soft-RoCE/TCP/兼容模式推导 RNIC/GDS 直通 |
| 生产经验 | 在真实服务中承担过责任并处理问题 | 将个人压测称生产运行 |

当前仓库仍是规划阶段；下表是目标证据，不是已完成能力。每章结束填 run_id、代码/PR 和未验证范围，再用于简历。

## 3. 章节、职责与目标证据

| JD 方向 | 章节/工作面 | 应积累的证据与自测问题 |
|---|---|---|
| 容量与量化 | Ch1 | 按模型/rank 算容量；量化 KV 的存取、质量与性能验证。为何 resident token 不等于 SLO 并发？ |
| CPU 卸载与数据搬运 | Ch2 | 实际恢复路径、批量/同步/buffer 管理；提交/等待/复制分解。所谓零拷贝省哪一步？ |
| 生命周期 | Ch2 起贯穿 | 引用与在途任务，取消、晚到完成、部分失败、满池和 reset/shutdown；何时才可回收？ |
| 本地 IO/存储后端 | Ch3 | io_uring/O_DIRECT、布局/索引、资源上限、短 IO、正常与失败回归；何时重算更便宜？ |
| 淘汰/预取与准入 | Ch2–Ch3 | 在真实决策点执行的策略/预算，不只离线模拟；命中率提高为什么可能仍变慢？ |
| 跨实例共享/服务 | Ch4–Ch5 | 模型/revision/dtype/layout 身份、完整对象发布、驱逐/读并发、远端故障；不把部署 Mooncake 写成自研 master |

| 全局调度与事件 | Ch7 | 复用 router 后的定点改造/测试，缓存视图新鲜度、活跃负载、恢复成本与背压 |
| 模型/布局适配 | Ch8 或提前出现的需求 | 一次确实改变缓存假设的适配或兼容验证，说明哪些旧假设失效、哪些组合仍不支持 |
| 可观测性 | 首版原始数据 → Ch5 服务化 | 指标分母、store/load/失败与队列、路径归因和可验证的告警；不是只搭 Grafana |
| 引擎/系统基本功 | 全程 | 一条请求的实际源码路径；C++ 所有权/并发、Linux 调试、算法持续练习 |

## 4. 边界与代表性覆盖

- **KV 量化**：建议实际验证一种兼容配置；权重量化不等于 KV 量化，使用现成算法不等于算法研发。
- **推测解码**：理解临时/已确认 token、状态提交与回滚；选定部署或修改涉及时测一个组合，不要求训练 draft。
- **FlashAttention/kernel**：先读接口与布局，必要时改搬运/转换 kernel；专职算子岗位还需要额外实现证据。
- **GDS**：主机中心次级层不能直接变成 GPU 目标路径；不支持的硬件上只理解/兼容模式学习，不冒充直通。
- **SPDK**：项目外理解与小实操起步；需要真实设备时再扩展，不凑一个无需求后端。
- **CXL、NVMe-oF、TRT-LLM、CacheGen/CacheBlend 等**：按岗位需求到认识/方案比较，不承诺工程覆盖。
- **Raft、其他分布式存储系统**：讨论概念和已有实习经验，不硬凑自研协议或虚构 Redis/Alluxio/Ceph 经历。
- **SGLang/Mooncake/LMCache/FlexKV/3FS**：至少一个主引擎深入，其余按实际接口或对照学习，不同时通读全部。

## 5. 面试准备与项目出口

每章形成「现象—假设—实验—改动—正确性—代价—边界—本人责任」证据卡。深度在项目中积累，面试前补广度、系统对比与迁移问答，见 [09](09-learning-roadmap.md)。不保证一份项目覆盖所有面试题。

第一份可投递成果可以早于全部章节：一个可信 baseline、一条真实路径、一次解释得清的干预/负结果、必要回归，以及一处本人负责的修改/适配。没有跨节点实测就不写跨节点落地，尚无实现就不把 benchmark 包装成存储系统开发。

反问聚焦团队实际边界：KV 组管哪些 scheduler/allocator/传输模块，模型适配由谁负责，驱逐与路由怎样协作，PD 故障如何处理。目标是证明能接管一段工作，不是展示尽可能多的技术名词。
